行程資料用量卡

旅客在行程中最常問的一件事：我還剩多少？目前 Roam 沒有任何地方回答它 —— 要知道用量得離開 app 去看電信商介面。這張卡把答案放進行程頁，並在快用完時給出下一步。

這份檔案怎麼用

  • 這是規格本身，不是規格的簡報 —— 討論結論直接寫回這個檔案。
  • 每個 data-decision 討論後必須是 agreed 或 deferred，不能留在 open。結論寫進 data-resolution。
  • Mockup 是活的 HTML/CSS：#mock-card、#mock-card-low，顏色與尺寸集中在 .phone 的 CSS 變數。改了就會看到。
  • 每條驗收條件都要有 data-check。human 是合法答案；沒宣告不是。
  • Changelog 只能追加。改了哪一條、為什麼，一行一筆。
Slide 1

它出現在哪，取代了什麼

位置是行程詳情頁 /zh-TW/trips/[id] 的第一張卡，在行程時間軸之上。 它取代的不是某個既有元件 —— 而是取代「旅客切出去查電信商」這個動作。

因此它的成功條件不是好看，是不用點就答完：剩多少、還夠不夠用到行程結束、 不夠的話下一步是什麼。三件事，在摺線以上。

先說旅客的實際行為：現在他們要離開 app。這張卡的存在理由是消滅那個動作，不是增加一個功能。

強調「不用點就答完」——這會直接決定後面兩個決策怎麼選。

Slide 2

兩個維度的難題

「還剩多少」其實是兩個數字：剩餘流量和剩餘天數。 它們會不同步 —— 流量剩 80% 但明天到期，跟流量剩 5% 但還有六天，是完全不同的處境， 而且需要不同的下一步。

流量和天數，哪一個當主要數字？

  • 流量主導（目前 mockup）—— 大字是 GB，天數退為次要。旅客對流量更焦慮，但「明天到期還有 8GB」會被藏起來。
  • 取較緊的那個—— 卡片自己判斷哪個先耗盡，把那個放大。誠實，但同一張卡在不同時候長得不一樣，可預期性差。
  • 兩個並列—— 都用中等字級。不用選，但失去「一眼看完」，而那正是這張卡的目的。

這是這次要談的核心。先示範 A 的失效情境：讓他想像「明天到期但還有 8GB」這張卡長什麼樣 —— 大字寫 8.0 GB，旅客完全不會警覺。

B 是我傾向的，但要老實說它的代價：同一張卡在不同時候長得不一樣。問他能不能接受。

主要動作是「加購一個具體方案」還是「去看所有方案」？

  • 具體方案 + 價格（目前 mockup）—— 一鍵完成，但我們替旅客選了。選錯的話這個按鈕就是噪音，而且它長得像廣告。
  • 導到比較頁—— 誠實，但多一步，而且那一步發生在他正焦慮的時候。

先問他一句：這張卡是不是在賣東西？他的答案會直接決定 A 還是 B。

如果他選 A，要追問「我們怎麼決定推薦哪一個」—— 那會變成一條新的驗收條件，現在還沒有。

驗收條件

每一條都宣告了誰來檢查。human 是合法答案 —— 沒宣告才不是。

#條件檢查方式
c-1卡片出現在行程詳情頁第一位，時間軸之上 smoke · routes.json
c-2healthy 與 low 兩個狀態在 390 / 1280 / 1440 都有 baseline visual gate
c-3「約可再用 N 小時」由近 3 日用量推估，用量為 0 時不顯示推估而非顯示無限大 unit
c-4所有文案在 zh-TW 與 en 都存在，數字用 locale 格式 i18n-parity
c-5資料讀取失敗時卡片顯示「暫時讀不到用量」並保留行程資訊，不顯示 0 GB state driver
c-6旅客一眼就能判斷「夠不夠用到行程結束」，不需要心算 human

c-6 是唯一需要人判斷的。這是刻意的 —— 它就是 D-1 要解決的問題， 而 D-1 一旦決定，它可能可以降級成一條可測的規則。討論時值得試試看。
